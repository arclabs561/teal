# Public listen identifiers and search

Run `../verify-local.sh` with Node 24. This audit replays saved public data. The 22 recording search snapshots, two unavailable capture targets, and response timestamps are in `paired-responses.json`. The eleven release tracklists are under `tracklists/`. The four `page-*.json` inputs retain music metadata and page-level provenance. Account identifiers and listening timestamps were removed from individual rows. The page URLs and bounded refresh URLs describe the source. Use the pinned files for a stable CI run.

## Where the identifiers come from

Four bounded public ListenBrainz pages provided 160 listens and 123 distinct title, artist, and release inputs. Forty rows supplied a release ID in `additional_info`, all from one page. ListenBrainz returned a release ID in its own mapping on 131 rows, including 91 without a submitted release ID. The recording ID counts were the same. This convenience sample has repeated listens and different client pipelines. Broader coverage across listeners, providers, and Teal users remains unmeasured. [ListenBrainz JSON documentation](https://listenbrainz.readthedocs.io/en/latest/users/json.html)

Nineteen rows on the ID-rich page disagreed on an exact release ID. The disagreements cover two album pairs. *Profound Mysteries II* switched from a digital edition to a CD on thirteen rows. *Interloper* did the same on six. The submitted recording matched the mapped recording on every affected row, and both editions contained it. This is an observed change in edition identity. The audit did not establish that exact edition provenance affects Teal’s current display or aggregation. Piper copies submitted IDs and then prefers the ListenBrainz mapping when present. For recorded listens, an existing recording ID skips hydration. The rewrite’s manual picker starts from song, artist, and optional album text. It writes the release ID after the user confirms a result. The import and picker paths therefore have different inputs. ## What a single search request can recover

The selector ranks source text triples by a fixed SHA-256 seed and takes up to two distinct release groups from each page. It excludes previously studied release names. The release lookup confirms a catalog track for six selections using tracklist positions and corroborating text or source metadata. The six include two submitted release IDs and four mapped release IDs. The five complete pairs each use cleaned provider text, one exact query, and a limit of five results. A sixth pair has an unavailable release-ID capture. Two further variants lack sufficient release evidence for a label.

| First exact query on five complete pairs | Top one | Top five |
| --- | ---: | ---: |
| Release title | 3/5 | 4/5 |
| Release ID | 4/5 | 5/5 |

The release ID moved the tracklist recording of “Polyrytmi” from second to first in the raw order. The #253 ranker also put the correct “Polyrytmi” first using the release name and one request. The release ID recovered the movie version of “Sparkle” at rank two. The paired changes are descriptive for this small sample. The two incomplete label cases are a provider-listed slowed version of “Golden Brown,” mapped to a compilation without that version listed, and a claimed 2014 remaster of “Beware of Darkness” mapped to a 1987 CD. MusicBrainz often uses one recording ID for different mastering or playback speeds. These cases establish edition discrepancies. ## Sparkle and the search budget

The public listen says `Sparkle - movie ver.`, with a submitted length of 534,120 ms and track number 3. The artist’s release listing puts the English version at track 24 and the movie version at track 3 on the bonus disc. The MusicBrainz tracklist lengths are 411,493 and 535,200 ms. ListenBrainz mapped the English version, which differs from the submitted title and is about 123 seconds shorter. The movie version is about one second from the submitted length. [Artist tracklist](https://radwimps.jp/en/music/12784/) · [MusicBrainz tracklist](https://musicbrainz.org/release/a7fc3d41-d645-418e-a5d2-960a835b04e0)

Replaying the current #253 orchestrator with captured 25-result responses took two requests. The album query returned zero. The query without the album retrieved both versions and ranked English first. Using the release ID with the cleaned song title retrieved both in one request, still with English first. Constraining either literal English title with the release ID returned zero. The same query using the catalog’s indexed Japanese title returned the movie version first. Generalizing this spelling probe would require testing cases where the indexed title is unknown at search time. [Current #253 source](https://github.com/arclabs561/teal/blob/67aa7381f5b771ce1ba8771b991cdce48c61625f/apps/amethyst/lib/searchOrchestrator.ts)

Using the submitted duration to reorder the two candidates already returned by #253 puts the movie version first with zero additional requests. A nearest-duration rule on “Polyrytmi” chooses a different recording from the submitted release tracklist. Keep duration as supporting evidence alongside version and edition. For the text-only picker, this case supports showing the alternatives clearly. For Piper, it supports a provider-specific test that can distinguish a mapped recording from a recording corroborated by source evidence. Piper’s behavior here is established from source.
